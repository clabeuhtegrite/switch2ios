# Mario Kart World on iPhone (in progress)

The iPhone app is the same build as the Mac app: the game's code rewritten once on the Mac, its shaders translated ahead of time, nxnative's iOS front end (`nxnative/dm/ios`) around it. The rewritten modules are compiled into the app's signed executable, so it needs no JIT. Targets: iPhone 17 Pro (A19 Pro), iPhone 18 Pro and iPhone Duo (A20 Pro), all with 12 GB of memory, installed with [LiveContainer](https://github.com/LiveContainer/LiveContainer).

**Status:** nothing has run on a phone yet. The first step is measuring the game on the Mac with a phone's budget (below).

As for the Mac app: everything is built on your Mac from your own dump, and nothing made from it leaves your devices. The IPA holds the game's rewritten code: never share it.

## What differs from the Mac

| | Mac (M1 Max, as tested) | iPhone (12 GB) |
|---|---|---|
| Memory the app may use | 13-16 GB in play, peaks of ~18 GB | about 6 GB, then iOS ends the app |
| Address space in one block | 20 GB (the profile's guest block) | about 6 GB without the extended virtual addressing entitlement |
| GPU | M1 Max | A19 Pro / A20 Pro (BC textures from the A17 Pro on) |

The game is made for the 9.5 GB a Switch 2 gives it, and the host tells it the same (`app_pool` in the profile). Fitting it into a phone means a smaller guest block and pool the game still runs with, and less memory of the host's own (Metal textures, caches).

## Building

1. Once: Xcode with the iOS platform and the Metal Toolchain (Xcode → Settings → Components), and `brew install xcodegen`. `./switch2mac.py setup` lists what is missing.
2. `./switch2mac.py build <dump folder>`, as for the Mac.
3. `./switch2mac.py ios`: the shaders again with Metal libraries for iOS as well (the first time about as long as the Mac's), then nxnative's `build_ipa.sh` packs `work/MarioKartWorld.ipa`, unsigned. `./switch2mac.py ios --xcode` makes an Xcode project instead (`work/xcode`), to sign with your own team and run on the phone with Xcode's log and debugger.

The game files stay out of the IPA (`DM_COPY_ROMFS=NO`): the app carries only the identity of `work/extract/RomFS.img` and uses that image from its Documents folder. `./switch2mac.py ios --romfs` packs them into the app instead, as `work/MarioKartWorld-full.ipa` (the slim one stays beside it): one file to install, about 23.7 GB, stored without compression.

## Installing with LiveContainer

1. Install `work/MarioKartWorld.ipa` in LiveContainer.
2. Copy `work/extract/RomFS.img` into the app's Documents folder: in the Files app, On My iPhone › LiveContainer › Data › Application › (the app's data folder) › Documents. Any letter case of `romfs.img` works; a copy cut off partway is ignored.
3. Start the app from LiveContainer. Its log is `Documents/log.txt`, its memory statistics `Documents/memstat.tsv`.

With `work/MarioKartWorld-full.ipa` (`ios --romfs`), step 1 alone does it, but the phone needs room for the game twice while LiveContainer installs it (the IPA and the app it unpacks, about 47 GB, more if the IPA is first saved in Files), and every new build means sending and installing all of it again. While the app keeps changing, the slim IPA with the image copied once into Documents is the quicker way: a new build is then 434 MB, and the image stays. A `Documents/romfs.img` is used before the one inside the app.

LiveContainer runs the app inside its own process, so the app has LiveContainer's entitlements, not its own. The log's first `[mem] address space` line (`DM_VA_PROBE`) says how large a block it can reserve: about 6 GB means no extended virtual addressing.

## Switches

`games/mario-kart-world/env_ios.txt` holds the phone's switches; `switch2mac.py ios` packs it into the app, and a `Documents/env.txt` on the phone overrides any of them without a rebuild (one `KEY=VALUE` per line). The launcher screen has the rest (handheld by default on the phone, Performance mode on).

| Switch | What |
|---|---|
| `DM_ALIAS_SIZE` | the alias region, where the game maps memory on demand (profile: 10 GB) |
| `DM_HEAP_REGION` | the heap region (profile: 9.5 GB) |
| `DM_APP_POOL` | the application pool the game is told, from which it sizes its heap (profile: 9.55 GB) |
| `DM_VA_PROBE=1` | log the largest block of address space the process can reserve |
| `DM_MEMSTAT=<file>` | memory every second: footprint, what iOS has left, Metal, and the guest / code / malloc / GPU split; with the guest in a file, its dirty pages, its blocks on disk and the free space, the process's and the system's paging and disk traffic, and what each sample took; other parts of the host can write marks between the rows (`# ` lines) |
| `DM_MEMSTAT_WALK_EVERY=<n>` | once a memstat sample takes over 5 ms (a `[RED]` line says so, and how much of it the region walk took), the memory regions are walked only every n samples, the rest still every second: the walk counts every page of the guest file's mappings and may hold up the game's page faults (default 1, every sample) |
| `DM_REGIONS=<file>` | the game's address regions every 2 s, with what is mapped in each |
| `DM_OPMODE=0` | handheld mode |
| `DM_NVN_DESWZ_GPU=0` | textures deswizzled on the CPU: a pool that holds only textures never becomes resident, which on iOS wires the whole pool |
| `DM_NVN_DESWZ_GPU=2` | textures deswizzled on the GPU from a copy of their storage made for each upload: their pool stays out of the residency set, at the GPU's speed |
| `DM_NVN_SPARSE_FREE=1` | a sparse texture's tiles the game unmaps (the terrain) give their memory back for its next tiles, and its heaps go with the texture |
| `DM_NVN_SPARSE_SHARE=1` | the tiles of such a texture that the game maps over the same physical 64 KB tile share one Metal tile, uploaded once (Mario Kart World maps each page of its terrain into 4 tiles); a tile it unmaps gives its memory back, as with `DM_NVN_SPARSE_FREE` |
| `DM_NVN_SPARSE_RT=1` | large sparse textures the game draws into get memory only for the 64 KB tiles it has mapped, as on the console (Mario Kart World: 10 such textures, 3.1 GB made whole) |
| `DM_NVN_CS_SHARED_SPILL=1` | a compute shader asking more shared memory than Metal's 32 KB a thread group keeps it in device memory (Mario Kart World's skeleton shaders ask 48 KB); Mac only for now, the variant being compiled from the shader's MSL |
| `DM_GUEST_FILE=1` | the guest's memory in a file in the temporary folder (sparse, unlinked at once), mapped shared at the same addresses: its pages leave the footprint, and the kernel can write them to the file when it needs the room; a `[mem] guest file` line every 10 s says what the file holds on disk, what the process wrote, read and dirtied, its page-ins, the footprint and its peak, and the free space; the game is stopped (exit code 87) when the file's disk falls under `DM_GUEST_FILE_MIN_FREE`; `[RED]` lines say when the guest stays anonymous and why (the file not made, unlinked, sized or mapped; on iOS a protection class that closes when the phone locks and cannot be set to C; on the Mac less free space than `DM_GUEST_FILE_MIN_FREE` and 8 GB), and what could go wrong with the file (not on a local APFS volume, not sparse, under 10 GB free at start or 2 GB later); files an earlier run left in the folder are removed at start, and a map in the alias region leaves pages that already read 0 as they are (the `[mem] alias region mapped` line counts them) |
| `DM_GUEST_FILE_MIN_FREE` | with `DM_GUEST_FILE=1`: the free space on the file's disk (statfs `f_bavail`, without what the system could purge), read every second, under which the game is stopped (default 5G; whole MB: bytes, K, M or G; 0 = never); on the Mac the guest stays anonymous unless the disk has this and 8 GB free at start |
| `DM_GUEST_FILE_PUNCH=1` | with `DM_GUEST_FILE=1` (off by default): what the game gives back (UnmapPhysicalMemory, a smaller heap) leaves the file too, as holes punched under whole host pages, unless a memory pool or a virtual pool still holds them; a self-test at start turns it on only when a punched page reads 0, and the `[mem] guest file` line counts the punches, those vetoed, the bytes, the time and the longest punch |
| `DM_GUEST_FILE_CHUNK=<size>` | with `DM_GUEST_FILE=1` (off by default, and not in `env_ios.txt` until `tools/nocopy_cross.m` and a game run pass on a Mac): the guest's memory in several files of that size (whole MB, K / M / G; `guest-<pid>-<i>.mem`, the last one shorter), each mapped over its own part of the block, instead of one file as large as the block: the stall at the system's periodic flush grows with the file (on a 16 GB M5 Mac without the game, 1 GB touched: up to 126-148 ms with one file of 20 GB, 4 ms with 20 files of 1 GB). 1G first; the next Mac run with the game compares 1G, 512M and 256M. At least 64 MB and at most 1024 files (the size is raised), one file at or above the block's size; when the files cannot all be made or mapped, a `[RED]` line says why and the one file is tried instead. A memory pool across two files has not been tried on a Mac (the host stops if Metal refuses its buffer; a `[mem] memory pool … spans more than one guest file` line says when one crosses) |
| `DM_FAULT_RETRY_CAP=<n>` | a fault the page fault hooks claim n times in a row with nothing changed, at a page that cannot be read although its protection allows the access, takes the crash path with a `[RED]` line (address, si_code, count) instead of being retried forever; 256 with `DM_GUEST_FILE=1`, off otherwise; 0 turns it off |
| `DM_NVN_MEMANY_MINCORE=0` | storage checks read every page that can be read again, the never-written ones and the guest file's holes included (to measure what skipping them saves) |
| `DM_NVN_HOLE_CHECK=1` | with `DM_GUEST_FILE=1`, storage checks and deswizzle copies read the guest pages they take for holes of the guest file all the same, and a `[RED] [mem] guest file: … holds data` line names any that holds data (to check the hole skip on a Mac; it brings those pages in, and a page the game writes during the check can show up too) |
| `DM_NVN_FRAME_VM=0` | no paging counters (on by default): the `[longframe]` lines without the frame's page-ins, MB read, faults and system page-outs, the TSV without `@vm_pageins`, `@vm_faults`, `@disk_read_mb` and `@sys_pageouts`, and the `[nvn] frame interval` line without the frames over 33.3 / 50 / 100 / 200 ms |

Sizes are bytes, or whole K / M / G (`DM_APP_POOL=4G`). The guest block is 256 MB + alias region + 256 MB of stacks + heap region; its size and parts are logged at start (`[mem] guest block`).

## Fitting into a phone's memory

On the Mac first, where a run that fails costs a minute:

1. `./switch2mac.py run --phone`: the phone's switches and launcher defaults (handheld, pipelines through the MTLDevice as on iOS), with `work/logs/memstat-*.tsv`, `regions-*.tsv` and `disk-*.tsv` beside the log. Play the same route each time (title, a Grand Prix race, some free roam). The `[mem]` lines give the heap the game asks for and how deep it uses the alias region.
   The `[mem] memory pool` and `[mem] large texture` lines say what of the large pools and textures is in memory and what put it there; the control file's `texmem <path>` lists every Metal allocation and pool at that moment. The control file's `mark <label>` (`mark race start`) puts `[mark] <label> t=… s` into the log and a `# mark …` line into the memory statistics, to find the same moment in both.
   With `DM_NVN_SPARSE_RT=1`, `[mem] sparse render target` lines give each such texture's tiles backed and the Metal tiles in all; `texmem` ends with the totals, the terrain's sparse textures (heaps, tiles bound, tiles given back with `DM_NVN_SPARSE_FREE=1`, and for each one the physical pages behind its tiles: fewer pages than tiles means the game maps a page into several tiles, which `DM_NVN_SPARSE_SHARE=1` gives one Metal tile) and the deswizzle copies of `DM_NVN_DESWZ_GPU=2`. With `DM_GUEST_FILE=1` it also gives what finding the guest file's holes cost (`guest file holes`: extents asked, time in all, the longest). Once the host punches holes, it also gives the punches the Metal layer was asked about and refused (`guest file punches`: over a memory pool, over a finalized pool's buffer still alive, over a virtual pool's pages or with its lock busy, with the pool table's lock busy).
   `tools/memstat.py` sums the statistics up (peak, median, a timeline, the time above the budget; `--from` / `--to` for one part of the route); `run --phone` prints it when the game exits, and it reads the phone's `Documents/memstat.tsv` as well. It also lists the marks other parts of the host write into the file and gives the disk writes, page-ins and page-outs per second for each section between marks (`--sections <regex>` splits at some marks only). With `DM_GUEST_FILE=1` it lists the file's flushes (its dirty pages falling by 64 MiB or more within 2 s, with their size and spacing) and names the slowest sample.
2. Smaller layouts: `./switch2mac.py run --phone DM_APP_POOL=… DM_HEAP_REGION=… DM_ALIAS_SIZE=…`. Mario Kart World 1.0.0 asks for a heap of the pool less 1.57 GB, and with a pool of 8 GB or less (a heap of 6.43 GB or less) it stops within a second of `nnMain`, before it mounts its RomFS, on a null pointer (`CRASH sig=11 addr=0x10 pc=main+0x3e8b58`), with the profile's alias region as with a 4 GB one; 9.55 GB works. A smaller pool saves nothing anyway: the heap is address space, and the memory is the pages the game touches (5.6 GiB in a race). So the phone needs room for that heap: about 13 GB of address space with the alias region it uses (up to +4.5 GB), which only extended virtual addressing gives (`DM_VA_PROBE=1` says on the phone).
3. The target: a footprint (`memstat`) under about 5.5 GB through a whole race. Without extended virtual addressing the guest block would also have to fit in about 5.5 GB, which Mario Kart World's heap does not allow (step 2).
4. The game's own heaps: Mario Kart World sizes them from `System/HeapSize/*.HeapDef.byml.zs` in its RomFS (55 heaps, 6.9 GB in all, 2.4 GB of it for textures). `tools/heapdef.py list` shows them from your dump, and `tools/heapdef.py set <heap>=<MiB> ...` writes copies with those heaps resized into `work/overlay`, which a run reads before the RomFS with `DM_ROMFS_OVERLAY=<that folder, absolute>` (`DM_FSLOG=<file>` lists the files the game reads, to see that it reads them). Without the switch the game reads its own files. Mario Kart World 1.0.0 reads `Default.Nin_Ounce_NVN2` once, 0.65 s in, after it mounts its RomFS (so these sizes are not what stops it with a small pool, step 2). A heap saves memory only where the game fills it: with its texture heap at 1600 MiB instead of 2395 (`tools/heapdef.py set aglTextureDataManager=1600`, a title, a race and 3 minutes of free roam on the 16 GB MacBook Air), the picture was unchanged and so was the footprint (11.2 GiB in a race, against 11.15 to 11.55 for runs without it): the memory pools were 0.9 GB smaller, but the game had not touched those pages. Compare the memory statistics with a run without the overlay, and check the picture (texture detail, textures appearing late).
5. The guest's memory out of the footprint: with `DM_GUEST_FILE=1` it lives in a file, and iOS does not count pages a file backs against an app (phys_footprint counts anonymous memory). They take the same memory while they stay in it, and the kernel writes them to the file when it needs the room. Measured with Mario Kart World on the 16 GB MacBook Air (`run --phone DM_PSO_MANIFEST=off DM_GUEST_FILE=1`: a title, a race and 3 minutes of free roam, on a Mac short of free memory throughout): the footprint peaked at 5.62 GiB instead of 11.58, 4.6 GiB of it Metal's; the picture was unchanged and the median 60 fps, but long frames were more frequent (in the race 42 over 100 ms against 4, in free roam 16 against none, the worst 295 ms against 94), the first frame came 24 s later, and the system wrote about 25 GiB to its disk in 10 minutes (about 1.5 GiB a minute in free roam), the kernel writing the game's pages out to make room. It changes what iOS counts, not the memory in use: on a phone the kernel can only make room by writing out pages the GPU does not hold. UnmapPhysicalMemory's MADV_FREE gives nothing back on these pages; `DM_GUEST_FILE_PUNCH=1` punches them out of the file (not measured yet), and the `[mem] alias region mapped` lines say how much the game gave back and how much MapPhysicalMemory zeroed again. With the file in use the game is stopped when its disk falls under `DM_GUEST_FILE_MIN_FREE` (5 GB by default: a phone with less free space quits a second after start, which `Documents/env.txt` can change; the figure is statfs's, which leaves out what iOS could purge, so Settings can show more), and on the Mac a run with less than that and 8 GB free keeps the guest anonymous (a `[RED]` line says so), so make the room before a measuring run.
   No guest page being anonymous, the skip of never-written pages no longer applies to them. In its place, a guest page that is out of memory and lies in a hole of its file (`SEEK_DATA`: never written out, or punched) counts as never written, in the storage checks and in the deswizzle copies; a page written out and freed since is read (`[mem] large texture` lines and `texmem`: MB skipped as holes of the guest file). A page that cannot be read (the game's unmapped memory, its heap past SetHeapSize) counts as zeros without being read, as in the staging copies, where reading it would stop the host with SIGBUS. A hole punch never falls under a memory pool's zero-copy buffer (registered, or finalized with its buffer still alive) or under the guest pages a live virtual-pool run maps. The Metal layer's veto refuses it, and also refuses it while the pool table's lock or the virtual pools' lock is busy.
   Each `[longframe]` line ends with the frame's paging: page-ins, MB read from disk, faults, and the system's page-outs read at its end; the `[nvn] frame interval` line counts the frames over 33.3 / 50 / 100 / 200 ms every 300 frames. A long frame with page-ins and megabytes read is the guest's pages coming back from the file, or the game reading its RomFS (`DM_FSLOG` tells which); system page-outs are the kernel writing pages out to make room. A page of the file that cannot be read back stops the host with `[RED] page fault at … it does not come in` instead of a thread retrying it forever (`DM_FAULT_RETRY_CAP`).
   The memory statistics show the file's side. `guest_dirty` is the pages the game has written that are not back in the file yet, what the next flush writes. `file_alloc` and `disk_free` show the file's room on disk. The disk writes and the system's page-outs are given per second, so `tools/memstat.py` can show the flushes and what they write. If memstat's own region walk takes over 5 ms a sample (a `[RED]` line), `DM_MEMSTAT_WALK_EVERY=<n>` stops it from holding up the game every second; flushes can then only be seen where two readings are 2 s apart or less.
   `run` guards the disk the file is on (the host's temporary folder, or `DM_GUEST_FILE_DIR`) when the run uses the file (`DM_GUEST_FILE=1`, as with `run --phone`; `DM_DISK_GUARD=1` for any run): with under 25 GB free there it does not start the game; it logs the free space every 30 s (`[switch2mac] [disk]` lines), and once more 30 s after the game has exited, to show what the disk got back; under 5 GB it stops the game with a `[RED]` line (SIGTERM, then SIGKILL 5 s later; a full disk was not tried). `DM_DISK_GUARD=0` turns the guard off. With the file the host's own stop at 5 GB usually comes first (exit code 87; 1 when the guard stopped the game). `run --phone` also writes `work/logs/disk-<time>.tsv`, a row every 10 s: the internal disk's bytes written and read since the Mac started (from ioreg), vm_stat's page-ins, page-outs, swap-ins and swap-outs, and the free space. Differences between rows give what the system writes for the file. `DM_DISK_SAMPLER=0` or `1` turns it off or on for any run. Neither is a switch of the app.
   With `DM_GUEST_FILE_CHUNK` the guest is in several files, which shortens the stall at the system's flush of the file (switch table). Before it goes into `env_ios.txt`: `tools/nocopy_cross.m` on a Mac (a memory pool across two files under one no-copy buffer), then a game run with `DM_GUEST_FILE_CHUNK=64M` and one with `1G`, looking for `[mem] memory pool … spans more than one guest file`, `zero-copy buffer was refused`, `failed to create the zero-copy buffer` and `virtual pool remap … failed`.

What the runs find goes into `env_ios.txt`, then the IPA.
