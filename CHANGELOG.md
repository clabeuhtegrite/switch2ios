# Changelog

## Unreleased: iPhone port (switch2ios)

- `./switch2mac.py ios`: the iPhone app from the same build, through nxnative's iOS front end: Metal libraries compiled for iOS as well, an unsigned IPA for LiveContainer with the game files left out (`romfs.img` goes into the app's Documents), or `--xcode` for a project to sign. Not run on a phone yet (docs/ios.md).
- iOS build: the Metal backend compiles with the iOS SDK, which has no `mach/mach_vm.h` and no `MTLPixelFormatDepth24Unorm_Stencil8` name: on iOS the `readwatch` diagnostic samples accesses only (no second mapping of the page), and the texture-to-buffer copy compares that format by its value; the control file's `probewin`, which needs the Mac's probes, only logs a line on iOS (the app did not link without it). The Mac is unchanged.
- `./switch2mac.py ios --romfs`: the game files packed into the app, as `work/<name>-full.ipa` beside the slim IPA, the RomFS image stored without compression (Mario Kart World's profile stores `.img`): one file to install with LiveContainer, which then needs room for the game twice while it installs. Without `--romfs` the IPA stays as it was, the image copied into the app's Documents.
- `./switch2mac.py run --phone`: the iPhone app's switches and launcher defaults on the Mac, with memory statistics and address regions beside the log; `run --memstat` for the statistics alone.
- `tools/heapdef.py`: Mario Kart World's heap definitions (`System/HeapSize`) read from your dump, `list` giving each file's heaps as a tree with their sizes, and `set <heap>=<MiB>` writing copies with some heaps resized into `work/overlay`, which the host reads before the RomFS with `DM_ROMFS_OVERLAY`: to measure what smaller heaps save. The copies stay in `work/` with everything else made from the dump; `selftest` checks the reader and writer on made-up files. Measured with Mario Kart World on the 16 GB MacBook Air (`run --phone`): the game reads the copy, and with its texture heap at 1600 MiB instead of 2395 the picture and the footprint were unchanged (11.2 GiB in a race), the game having not filled that heap.
- `DM_GUEST_FILE=1`: the guest's memory in a file in the temporary folder, sparse and unlinked at once, mapped shared over the guest block at the same addresses, so that its pages leave phys_footprint, the figure iOS ends an app at, and the kernel can write them to the file when it needs the room (an iPhone app's anonymous memory can only be compressed). On iOS the app names the folder (`DM_GUEST_FILE_DIR`) and the file gets protection class C; when the file cannot be made or mapped the guest stays in anonymous memory, with a `[RED]` line saying why, and `[RED]` lines say what could go wrong with the file (not unlinked, not on a local APFS volume, not sparse, a protection class that closes when the phone locks, under 10 GB free at start or 2 GB later); a `[mem] guest file` line every 10 s gives what the file holds on disk, what the process wrote, read and dirtied, its page-ins, the footprint's parts and its peak, and the free space. Storage checks (`mem_any`) take a page that cannot be read as zeros without reading it, as the staging copies do: with no guest page anonymous they no longer skip the game's unmapped memory, and reading it would stop the host with SIGBUS. Off by default. Measured with Mario Kart World on the 16 GB MacBook Air (`run --phone DM_PSO_MANIFEST=off`, a title, a race and 3 minutes of free roam): the footprint peaked at 5.62 GiB instead of 11.58, the picture unchanged, but with more long frames, 24 s more to the first frame and about 25 GiB written to the disk in 10 minutes (docs/ios.md). Not run on a phone yet.
- Guest file (`DM_GUEST_FILE=1`), guards from the reviews before the next phone build: the free space on the file's disk is read every second, and under `DM_GUEST_FILE_MIN_FREE` (default 5G; whole MB: bytes, K, M or G; 0 turns the stop off) the game is stopped with a `[RED]` line and exit code 87 (the memory watchdog's is 86), before a full disk leaves the kernel no room to write the guest's pages out. The free space is statfs's (`f_bavail`), which leaves out what the system could purge, so it can be less than Settings or the Finder show. On the Mac the guest stays in anonymous memory, with a `[RED]` line, when the disk has less than that minimum and 8 GB free at start; on iOS the file stays, as anonymous memory there means a jetsam kill. A file that cannot be unlinked, and on iOS one whose protection class is not C or D and cannot be set to C, now leave the guest anonymous with a `[RED]` line (they were warnings only). `DM_GUEST_FILE_PUNCH=1`, off by default, punches holes in the file (`F_PUNCHHOLE`) under the whole host pages UnmapPhysicalMemory gives back and under the part of the heap a smaller SetHeapSize gives back, right after their PROT_NONE, unless a veto the graphics layer registers (`dm_guest_punch_veto_register`, dm.h) says a memory pool or a virtual pool still holds them. A self-test on one page at start turns it on only when the punch works and the page reads 0 (`[mem] guest file: hole punching on`, with what st_blocks did, marked `[RED]` when less than the page's room on disk came back), and a punch that fails turns it off. The `[mem] guest file` line adds the punches made and vetoed, the bytes punched, the time they took and the longest punch; the `[mem] alias region mapped` line adds what UnmapPhysicalMemory gave back so far and what MapPhysicalMemory zeroed over host pages opened before (these two with the file off too). Tested on Linux with stand-ins for the Darwin calls; not run on a Mac or a phone yet.
- `DM_GUEST_FILE_CHUNK=<size>` (with `DM_GUEST_FILE=1`, off by default; whole MB, K / M / G) puts the guest block in several files of that size, `guest-<pid>-<i>.mem` (the last one holds the rest), instead of one file as large as the block. Each file is made, unlinked and, on iOS, given protection class C as the one file is, then sized and mapped shared over its own part of the block, from its offset 0. Why: the stall at the system's periodic flush grows with the file. On a 16 GB M5 Mac without the game, with 1 GB of the memory touched, threads touching it stalled up to 126-148 ms with one file of 20 GB, 11-16 ms with one of 2 or 5 GB, and 4 ms with 20 files of 1 GB, for the same bytes written. 1G is the first value to try (20 files with the profile's 20 GB block); the next Mac run with the game is to compare 1G, 512M and 256M (the worst stall at the 30-s marks, and how many memory pools cross a file boundary) before a value is settled, and the switch stays out of `env_ios.txt` until `tools/nocopy_cross.m` and that run pass. The size is rounded up to the host page, is at least 64 MB (with a `[RED]` line) and is raised to make at most 1024 files; a size at or above the block's size means one file. When the soft descriptor limit is below the descriptors already open plus the files plus 64 spare, it is raised by at least the number of files, so the rest of the host keeps the room it had; if the system refuses that, it is raised only to the files plus 64, and if even that fails, a `[RED]` line says so. If the files cannot all be made, unlinked, given protection class C (iOS), sized and mapped, or if the Mac's disk has less room than the minimum plus 8 GB, none is kept (a file whose unlink failed stays in the folder, empty, until the next start removes it), a `[RED]` line says why, and the one file is tried instead; if that fails too, the guest stays in anonymous memory. A name that is already gone at the unlink (another process's start removed it in between) counts as unlinked. On iOS, when the class had to be set, one line says in how many of the files it was set, once the files are kept. With several files, `DM_GUEST_FILE_PUNCH=1` punches a range a piece in each file it spans, the vetoes asked once about the whole range, and the 10-s `[mem] guest file` line sums every file's blocks and says how many files there are. A memory pool or a virtual pool's run that crosses from one file into the next puts two file objects under one zero-copy Metal buffer or one remapped run: this has not been run on a Mac yet, mtl_pool_add stops the host if Metal refuses the buffer, and a `[mem] memory pool … spans more than one guest file` line (the first 8) says when a pool crosses. With the guest file (one or several), a map in the alias region leaves 4 KB pages that already read 0 (never written, or punched) as they are, instead of writing zeros the kernel then writes back; the `[mem] alias region mapped` line counts them separately. Files an earlier run left in the folder are removed at start, with one line: `guest-<pid>.mem` / `guest-<pid>-<i>.mem` files of this user whose process has ended; links are never followed. For the rest of the host, `svc_guest_files`, `svc_guest_file_nth` and `svc_guest_file_at` (dm.h) give an address's file and offset; `svc_guest_file_fd` is the one file's descriptor, and -1 with several files, so that code written for one file does without the file, as in anonymous memory, rather than ask the wrong one; the volume is fstatfs of `svc_guest_file_nth(0, NULL, NULL)`; the storage checks' hole test (nvn_mtl.m) and memstat's file_alloc use them. Tested on Linux with stand-ins for the Darwin calls; not run on a Mac or a phone yet.
- Guest file (`DM_GUEST_FILE=1`): storage checks and the deswizzle copies of `DM_NVN_DESWZ_GPU=2` no longer read guest pages that are out of memory and lie in a hole of their file (never written out, or punched). Such a page reads 0, and reading it brought a page of zeros in from the file, render targets of 128-256 MB included. A page written out and freed since lies in data and is still read, as is any page in memory. The file that maps the page is asked once per extent (`SEEK_DATA`, and `SEEK_HOLE` in data), never past the end of that file's part of the block, and always after `mincore`. When it cannot tell, a `[RED]` line is logged and every page is read as before; an ask that takes over 4 ms gets a `[RED]` line of its own (the first 4, then every power of two), so that a long frame can be traced to it. The `[mem] large texture` lines and `texmem` give the MB skipped as holes, and `texmem` the extents asked and what they cost. `DM_NVN_HOLE_CHECK=1` (off by default) reads those pages all the same and names any that holds data (`[RED]`), to check the skip on a Mac. The Metal layer also registers a hole-punch veto (dm.h): no punch falls under a memory pool's zero-copy buffer, whether the pool is registered or finalized with its buffer still alive, nor under the guest pages a live virtual-pool run maps. The veto only tries the pool table's lock and the virtual pools' lock, and refuses the punch while either is busy; `texmem` counts the punches asked about and refused, by cause. Without the guest file nothing changes but the new report fields. Not run on a Mac or a phone yet.
- Paging per frame (on by default; `DM_NVN_FRAME_VM=0` turns it off and leaves every line as it was): each `[longframe]` line ends with the frame's page-ins, the megabytes read from disk, its page faults and the system's page-outs read at its end (`; page-ins 12 (3.4 MB read), faults 410, system page-outs 0 in the 1.00 s to its end`), so that a long frame on the phone, where there is no TSV, can be traced to `DM_GUEST_FILE`'s pages coming back from the file. With `DM_NVN_TSV` (and in `DM_SLOWFRAME`'s lines) the frame rows get `@vm_pageins`, `@vm_faults`, `@disk_read_mb` and, every second and at long frames (at most every 0.25 s), `@sys_pageouts` (the system's page-outs since the previous such row) beside `@t_s`. The `[nvn] frame interval` line every 300 frames adds the frames over 33.3 / 50 / 100 / 200 ms and what a reading of the counters costs; past 50 µs on average in two windows of 300 frames in a row they are read every 4th frame (and at every frame that looks long), with a line saying so. The megabytes read count the game's own file reads (its RomFS) as well, and the faults the dirty tracker's write faults; iOS answers the system's counters only a few times a second for all apps together, and a frame that got the kernel's cached copy says `not read at its end`. Not run on a Mac or a phone yet; the cost was not measured.
- Control file (`DM_CTL`): `mark <label>` logs `[mark] <label> t=<seconds since start> s` and writes the same as a `#` line into the memory statistics (`DM_MEMSTAT`), so that a moment of a route (`mark race start`) can be found in the log, the `[longframe]` lines and `memstat` alike.
- Sparse virtual memory pools: `nvn_vpool_src_covers()` says whether a live run of one still shows guest pages in a range (and says yes when it cannot tell without waiting), for the Metal layer's veto on `DM_GUEST_FILE`'s hole punching: a punch there would zero what the GPU still reads through the alias. Each 2 MB leaf of a pool's page table keeps the guest addresses its entries were ever mapped from, so the check passes over a leaf that never mapped from the range without reading its entries.
- Page fault hooks: with `DM_GUEST_FILE=1` (or `DM_FAULT_RETRY_CAP=<n>`; 0 turns it off), a fault the hooks claim 256 times in a row (n) on one thread with nothing changed (same address and registers, pc not moved), at a page whose protection allows the access but which cannot be read, takes the crash path instead of being retried forever, with a `[RED]` line naming the address, si_code and the count right after the `CRASH` line: a file page that fails to come in faults as a dirty-tracker write fault does, and the tracker claims every write fault on a page it ever tracked. Only threads that ran crash_thread_init, which makes their thread-local storage, keep the count, so the signal handler never makes it. Without the guest file nothing changes. Not run on a Mac or a phone yet.
- Memory statistics with the guest in a file: each `DM_MEMSTAT` row now ends with the file pages mapped (`external`) and what the guest files hold: `guest_dirty`, the guest block's file pages written and not back in the file yet (what the next flush of the file writes); `file_alloc`, the guest files' blocks on disk (every file's, with `DM_GUEST_FILE_CHUNK`); and `disk_free`, the room left on their volume. Next come the process's footprint peak since launch, its page-ins, disk reads, writes and logical writes (`proc_pid_rusage`), and the whole system's page-ins, page-outs, swap-ins and swap-outs (counted in pages) with its free, inactive and compressor memory (`host_statistics64`). The row ends with what taking the sample took (`sample_ms`) and the host's clock (`t_host`, the seconds the log uses). Sizes are in MiB, and the header line gives each unit. A value that could not be read is `-`: no guest file, a call that failed, or the region walk left out. A `[RED]` line says when a sample first takes over 5 ms, and how much of it the region walk took: the walk counts the pages of every region, all of the guest file's with the guest in a file, and may hold the task's map and the file's object locked meanwhile, which holds up the game's page faults. `DM_MEMSTAT_WALK_EVERY=<n>` then runs the walk only every n samples while samples stay that slow; everything else is still read every second. The default is 1, every sample. `memstat_note()` lets other parts of the host write a mark (`# <text>`) between the rows; it is written under the rows' lock and flushed at once, so it is not for a signal handler, nor for every frame. `tools/memstat.py` reads the new columns and still reads older files, with unchanged output for files in the earlier formats (those of parts D, K and M). It also lists the marks and gives the disk writes, page-ins and the system's page-outs per second for each section between marks (`--sections <regex>` starts sections at some marks only). It lists the guest file's flushes (its dirty pages falling by 64 MiB or more within 2 s, a punch with `DM_GUEST_FILE_PUNCH` included: size, time and the time since the last one) and names the slowest sample. Not run on a Mac or a phone yet.
- `./switch2mac.py run`: a disk guard for the guest file, on when the run uses it (`DM_GUEST_FILE=1`, as `run --phone` does); `DM_DISK_GUARD=1` turns it on for any run and `DM_DISK_GUARD=0` off. Without it the run is as before (with `--phone`, `DM_DISK_SAMPLER=0` too). It watches the disk of the guest file's folder (`DM_GUEST_FILE_DIR`, a relative one taken from the run folder as the host takes it, else the host's temporary folder, `confstr(_CS_DARWIN_USER_TEMP_DIR)` on the Mac), and the free space it reads is statvfs's, without what macOS could purge. With under 25 GB free there, the run stops before the game starts and says why. While the game runs, the free space is checked every 2 s and goes into the log every 30 s (`[switch2mac] [disk]` lines). Under 5 GB the game is stopped before the disk fills: SIGTERM, then SIGKILL 5 s later if it still runs, with a `[RED]` line; the run then exits with 1, since the host's graceful exit returns 0. With `DM_GUEST_FILE=1` the host's own stop at the same 5 GB, read every second, usually comes first, and the run then exits with 87. Once the game has exited, the run logs the free space again 30 s later, beside the values at the start and at the exit, to show what the disk got back (Ctrl-C skips the wait). `run --phone` also writes `work/logs/disk-<time>.tsv`, a row every 10 s and one as the game exits: the internal disk's bytes written and read since the Mac started (ioreg's block storage statistics, the disk named in the file's first line), vm_stat's page-ins, page-outs, swap-ins and swap-outs (pages), and the free space on the guest file's disk, to measure what `DM_GUEST_FILE=1` makes the system write and page. `DM_DISK_SAMPLER=1` or `0` turns it on or off for any run. A tool that does not answer leaves its fields empty, and an error ends the sampler, never the game. Not run on a Mac yet: tested with a stand-in host and stand-ins for ioreg and vm_stat.
- `DM_NVN_VC_WAYS=<n>` (default 4, as before) lets a texture keep up to n cached Metal texture views (4 to 256). On Mario Kart World menus the view cache reused no view at all for minutes (iPhone test 3, t=546-646 s; Mac run A, t=168-235 s): about 21 views a frame were made again for the same ~4,100 textures, with no new texture, storage takeover or re-upload meanwhile, and malloc rose 2.5-3.6 KB a view made, about 300 MB on the phone, coming down only when views were reused again (cause inferred: more view keys a texture than its 4 places, looked up in a cycle). With n above 4, a texture whose places are all taken gets more (doubling up to n, at most 4096 places added in all), an empty place is filled before a view is replaced, and a view made from a replaced base texture no longer ends the lookup. `DM_NVN_VC_MAX=<n>` (default 16384, as before) caps the textures that hold views. The `texture views by texture` log line now also gives the views held, the cap and its emptyings, the places added, the misses (no entry, key not held, held only from a replaced base) and the views replaced.
- `tools/vmprobe.m`: a test program without the game, for the Mac (and later the phone), asking whether the kernel stops charging guest pages the host gives back while a Metal no-copy buffer wraps them, as one wraps every memory pool: a block reserved and made read-write as the guest heap, slices wrapped in no-copy buffers and filled with data that does not compress, then each slice given back one way (PROT_NONE, MADV_FREE and both orders of the two, MADV_FREE_REUSABLE with no buffer, with a buffer the GPU never used, read just before or 3 s before, or in a residency set, MADV_DONTNEED, new pages mapped over it, or through a second mapping). Each step prints the task's footprint, the host's internal, wired and free pages and the slice's pages present, dirty and reusable, then what a GPU read, a CPU read and writing the slice again charge; `--each` runs each case in a process of its own. About 1.1 GB for ten seconds. On the M5 MacBook Air (macOS 27.0.1): MADV_FREE_REUSABLE takes a slice off the footprint while the GPU does not hold its pages, and any later GPU use charges it again; on pages the GPU holds (used within the last 3 s, or in a residency set) the footprint drops but nothing is freed; PROT_NONE alone takes pages off the footprint without freeing them, and UnmapPhysicalMemory's order (PROT_NONE, then MADV_FREE) leaves them dirty where the reverse leaves them clean.
- `tools/nocopy_cross.m`: a test program without the game, for the Mac, asking whether a Metal no-copy buffer and a vm_remap run can cover a memory pool that crosses from one guest file into the next, as `DM_GUEST_FILE_CHUNK` can make one: three unlinked sparse files mapped shared back to back in one reservation, a 64 MB pool over the boundary of the first two and a control inside the third, each half written and partly written out, then the no-copy buffer, a GPU fill read back by the CPU and by each file, a residency-set commit with a GPU fill through a queue holding the set, a remapped run with a buffer and a GPU fill through it, and a buffer with two read-only pages at its middle; each line ends in `ok` or `FAIL`. Not run yet.
- `tools/memstat.py`: a memory statistics file summed up (peak, median and a timeline of the footprint, Metal and the guest / GPU / malloc split, time above a phone's budget); `run --phone` and `run --memstat` print it when the game exits.
- Host: `DM_HEAP_REGION` and `DM_APP_POOL` size the guest heap region and the application pool at launch (beside `DM_ALIAS_SIZE`; sizes take K / M / G), the guest layout is logged at start, and `DM_VA_PROBE=1` logs the largest block of address space the process can reserve (also when the guest block does not fit).
- iOS: `DM_MEMSTAT` and `DM_THRCPU` from the app's env files now start (they were read before the files were).
- Memory statistics split what Metal holds: the memory pools' no-copy buffers (those the GPU uses, and all), packaged textures (uploaded copies of pool bytes), other textures, heaps, other buffers, the pools' pages in memory and the pipelines built; `tools/memstat.py` shows them. `DM_MEMSTAT_DUMP` and the control file's `texmem <path>` write every resident Metal allocation and memory pool, one per line.
- Mario Kart World: 4 more shaders the game builds at run time, met in handheld mode, are in `runtime_shaders.tsv`, so a build takes them from the dump (the phone's settings drew the 3D scene black without them).
- Mario Kart World's sdk (SDK 19.3.3 for the Switch 2) gets nxnative's AddressRegionManager node area cut (1 GB → 62 MB at the start of the alias region), which no SDK-wide rule matched: its constructor opens with a pointer-authentication prologue. The game's address regions then start at alias +0.06 GB instead of +1 GB, the room a phone's smaller alias region needs. It applies to the Mac build too (a rebuild picks it up); nothing else changes there.
- Host memory: a texture's storage check at its first use skips pages never written (mincore) instead of reading them, which made the kernel back them with pages of zeros charged to the process (`DM_NVN_MEMANY_MINCORE=0` reads every page). Pure bookkeeping otherwise: the check's answer is the same. It applies to the Mac too.
- Memory diagnostics: `[mem]` log lines for memory pools of 64 MB or more (what of each is in memory at creation, and before and after it becomes resident, with the call site that first asked for its address) and for textures of 64 MB or more (how each was made, its pool's flags, what of its storage is in memory); `texmem` adds each pool's pages in memory, the pools made resident by call site, and the storage checks' bytes read and skipped. `DM_NVN_DESWZ_GPU=0` deswizzles textures on the CPU, so pools holding only textures stay out of the residency set (on iOS a resident pool is wired whole).
- Shaders: nx2_lower lowers SM86 constant loads (LDC) of 8 and 16 bits and with the .IL / .IS / .ISL modes, which Ryujinx's Maxwell frontend reads; it rejected them before. Loads that were already lowered come out the same.
- Shaders: nx2_lower lowers HSETP2 with a constant-buffer operand (SM86 `0x634`), FRND from a constant buffer (`0xb07`), local stores and loads of 64 and 128 bits and at a register address (`STL` / `LDL`, with any cache hint), and a branch with bit 32 set (taken for BRA.U, a uniform-branch hint; it read as a misaligned offset). In Mario Kart World these stopped two DriveRefreshUber vertex shaders (`program has no vertex shader` in the log; the LDC fix above was not enough for them), a DriveRefreshUber pixel shader and three effect shaders, the last 6 of its 6,863. A `build` or `refresh` takes them once the tool is rebuilt (delete `nxnative/dm/gfx/tools/nx2_lower/nx2_lower`). Instructions that were already lowered come out the same.
- Shaders: a program nx2_lower rejects is listed in `work/shader/rejects.tsv` with the instruction the capture or the lowering stopped at (opcode, byte offset, its four words), and the split's summary counts the reasons by opcode, so a missing instruction is named without a debugger.
- Memory: `DM_NVN_SPARSE_RT=1` makes the large sparse textures the game draws into placement sparse textures, with memory only for the 64 KB tiles that have a page mapped behind them, as on the console; what was drawn into a physical page follows it when the game maps that page elsewhere. Such textures over the same pages share their Metal tiles, so from the first one on every barrier makes aliased writes visible (as with image heaps). Mario Kart World has 10 of them, 3.1 GB of Metal memory when made whole. Measured with Mario Kart World on a 16 GB MacBook Air (`run --phone`, with the two switches below): 81 MB for its 10 textures through a whole route, and a race's footprint of 12.5 GB instead of 14.4, the picture unchanged.
- `DM_NVN_SPARSE_FREE=1`: a tile of a large sparse texture read from its pages (Mario Kart World's terrain arrays) that the game unmaps is unmapped too, and its Metal tile is reused by the texture's next tiles, so its heaps grow only to the most tiles mapped at once; such a texture's heaps also go with it. `texmem` gives each one's tiles bound and the physical pages behind them. Before, both stayed for good (the heaps went from 2.2 GB at the title to 3.1 GB after 11 minutes of free roam). In Mario Kart World it gave nothing back on that route: the game never unmapped a terrain tile (see `DM_NVN_SPARSE_SHARE`).
- `DM_NVN_DESWZ_GPU=2` deswizzles textures on the GPU from a copy of their storage made for the upload and released with it, so their pools stay out of the residency set as with `=0`, without the CPU's cost (Mario Kart World with `=0`: 18 fps in a race). The copy skips pages never written, and gives zeros for pages that cannot be read: a texture's storage can reach such pages past the data its levels use (Mario Kart World: one of 1.4 MB, from 28 KB before its end), and the first run stopped there with SIGBUS. Mario Kart World on that Mac: 31 fps in a race (18 with `=0`) and 26 in free roam, the picture unchanged.
- `DM_NVN_SPARSE_SHARE=1`: the tiles of a large sparse texture read from its pages that the game maps over the same physical 64 KB tile share one Metal tile, uploaded once for all of them and given back when no tile holds it; a tile the game unmaps is unmapped too. Mario Kart World maps each page of its terrain arrays into 4 tiles (it moves a layer without unmapping the old one): with `DM_NVN_SPARSE_FREE=1` alone their heaps reached 4.4 GB by the end of free roam over 1.6 GB of pages, and one array its 2 GB cap (`tiles past 2048 MB stay zero`). Tiles mapped in part, to scattered pages or at a level's edge keep a Metal tile of their own. `texmem` gives each texture's physical tiles with a Metal tile. Measured with Mario Kart World on that Mac (part D): its terrain arrays' heaps stay at 2.0 GB from the title to the end of free roam (4.4 GB without it), the footprint's median over the route is 11.6 GB instead of 12.9, and it runs at 60 fps in every part of the route instead of 31 in a race, the tiles it maps again being no longer uploaded again; the picture is unchanged.
- `DM_NVN_CS_SHARED_SPILL=1`: a compute shader whose thread groups ask more shared memory than Metal gives (32 KB on every Apple GPU, M5 and A19 included) runs a variant with that memory in device memory, one slice per thread group, compiled from its MSL the first time a program uses it (`<key>_b.metal` beside the Mac library, so the Mac only for now). The build caps such an array at 32 KB, and the indices past it read and write outside it: Mario Kart World's six skeleton shaders (`Shader/Drive`) ask 48 KB, one 48-byte matrix per entry taken from the global thread ID, so in a dispatch of more than 10 thread groups every entry from 683 on was lost. The log names each shader that gets the variant and its dispatches. It is not what makes trees, cacti and rocks vanish in Mario Kart World: on a free-roam route and the title's demo those shaders ran with 1 to 3 thread groups, under the cap.
- iPhone settings (`games/mario-kart-world/env_ios.txt`): the memory switches measured in part D are on, `DM_NVN_DESWZ_GPU=2`, `DM_NVN_SPARSE_RT=1`, `DM_NVN_SPARSE_FREE=1` and `DM_NVN_SPARSE_SHARE=1`, so the iPhone app and `run --phone` use them with no arguments; a `VAR=value` argument, or `Documents/env.txt` on the phone, still sets each one otherwise.
- Diagnostics for objects missing from the picture while their shadows stay (Mario Kart World's trees, cacti and rocks, for 0.6 s to a few seconds at a time, with the Mac's settings as with the phone's): with `DM_NVN_WAITS=1` the `[waits]` line also counts the render-enable blocks by how replay evaluated them, the draws inside blocks not drawn, and the samples-passed results written and those of 0 samples; `DM_NVN_RC_DRAWS=0` draws inside blocks evaluated false all the same (their clears are still dropped), and `DM_NVN_OCC_VISIBLE=1` makes every occlusion query read as visible. Both are off by default. With `DM_SHOT_BURST=<n>` (1-64), key 3 takes a burst instead of one screenshot: the next n presented frames as PNGs in a folder of their own, with the pass dump of those frames in the log (`DM_NVN_PASSDUMP_ALL=1` records every draw), so a frame where an object is missing can be set against one where it is drawn.
- Mac window: key 3 saves a screenshot of the picture as shown (the next presented frame at the window's size) as a PNG in `<DM_ROOT>/logs/shots` (`work/logs/shots` with `./switch2mac.py run`, beside the save folder for the app; `DM_SHOT_DIR` names another), with a log line among the frame lines: a player points at a picture problem as it happens.
- Apart from that cut, the storage check, key 3, the paging figures at the end of the `[longframe]` and `[nvn] frame interval` lines (`DM_NVN_FRAME_VM=0` leaves them out), the two figures added to the `[mem] alias region mapped` line, and the figures for the guest file's holes in the `[mem] large texture` lines and in `texmem` (0 without the file), the Mac app is unchanged unless these switches are set; `./switch2mac.py run` is unchanged without the guest file or `--phone`.
